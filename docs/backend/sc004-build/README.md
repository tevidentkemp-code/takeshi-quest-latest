The candidate browser sends POST `{action, request_id, body}` to `sq-match-control`. Controller operations require `X-SQ-Match-Controller`; admin operations require the exact permanent Supabase Auth bearer JWT. The Edge verifies that JWT with `getUser`, then derives its user/session IDs. SQL checks the permanent confirmed user, live `auth.sessions` row and private allowlist on every admin operation. Request JSON cannot supply those identities or a service credential.

Creation returns a server-minted UUID and `sqmc1_` capability. A server-only 32-byte HMAC key derives the capability from action, random request UUID and canonical initiation body. Exact lost-response retries return the same authority while the original registry is live; changed bodies conflict. Cleanup and pruning retain the consumed issuance receipt, so replay cannot bind that capability to a new UUID. Expired or revoked issuance retries fail closed. SQL stores only a SHA-256 hash. The random initiation request UUID plus its exact body can recover the capability through the public retry route, so that UUID is a recovery credential: keep it private in the durable cache and exclude it from logs/public persisted state. The server-issued match/game UUIDs provide no such recovery. Keep the issuance key across an operational rollback. A public match UUID, player name or old cached match cannot claim authority.

Gameplay API:

- `create_match`: `{mode, roster, target_wins, match_format, rules}`. Modes: official, practice, turbo, vs_shadow. `match_format` is series or single. Response includes match_id, canonical roster, mode, rules, expiry and capability. Guest Practice series retains match wins; single Practice/VsShadow permits one accepted game. VsShadow persists one real player under public Practice semantics. Its canonical completed state has mode/gameMode 'practice'; the prior issued-mode spelling 'vs_shadow' is accepted only under that exact controller, and an explicit competitive gameMode is denied.
- `reserve_game`: `{match_id, game_number}`. Returns minted game_id, number and pending/completed status. Pending slots are private; no public unfinished game triggers the broken historical finish-UPDATE high-score function.
- `reset_game`: `{match_id, game_id}`. Only the latest unaccepted slot may reset. A cleaned slot must reset before a subsequent game can reserve; accepted history is immutable.
- `update_roster`: `{match_id, roster}`. Identity remains canonical; initials, avatar_id, nickname and display_name may change only within this controller snapshot. Pre-accept removal to one downgrades to Practice. Accepted games are never rewritten. Existing late-entry UI preserves the before-target-17 and between-Games-1/2 rules; no elapsed-seconds rule was invented.
- `complete_game`: `{match_id, game_id, state, totals, winner_indexes?}`. The existing canonical board and dart format remain; server validates scope, dimensions and aggregate consistency. Accepted game, proper high-score route and current match wins commit atomically. An exact retry returns its receipt; a changed retry conflicts.
- `log_go`: accepted game, saved roster player, round/go and ordered start/end timestamps. Calls the restricted six-argument helper. The unused broken ten-argument overload is dropped.
- `append_event`: `{match_id, game_id, event:{player_id, round_index, dart_index}}`. Event identity/kind/points derive from the accepted board. No arbitrary client event payload is stored.
- `resume`, `renew`, `list_roster`, `revoke_controller`, `cleanup_game`, `cleanup_match` operate only on the live controller scope. Cleanup cannot remove accepted games. Renew extends the same secret by 24 hours; expired/revoked credentials cannot renew or adopt historical IDs.

Training API is separate from competitive matches: `create_training` takes `{player, mode, length, config}` and returns training_id/expiry/capability. Modes standard/tdb/select and lengths 0/10/15 match current source. `complete_training` takes `{training_id,payload}` with the existing training columns; completed and partial-go results contain their actual 1–3 darts, with exact aggregate validation. `resume_training` and `renew_training` require the same training capability.

`create_player` is INSERT-only and idempotent by exact request UUID/body. It never overwrites a same-name existing profile. `visit` accepts a UUID device_id, derives the current UTC server day, and inserts once per day/device. Global profile, history, repair, archive and destructive routes delegate to authenticated `admin_action` implemented in admin-command.sql.
